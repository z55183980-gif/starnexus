# 日志查询治理（2026-09-09）

## 边界

本次仅调整管理端查询，不实施保留期删除、自动清理、归档或分区迁移。
45 天是一次查询的最大跨度，不是数据的删除期限。历史充值、消费、退款、
管理和系统记录继续保留；可以按不超过 45 天的历史窗口查询。
现有人工删除接口不在本次改动范围内，它不具有自动保护计费类型的能力，
不能把它作为“安全清理”的实现使用。

## 已实现

- `/api/log/`、`/api/log/stat`、`/api/log/summary` 共用时间校验。
  - 未指定起止时间（包含兼容的 `0`）时，默认最近 45 天。
  - 只有结束时间时，起点为结束时间前 45 天。
  - 只有开始时间时，结束时间为当前时间，再执行跨度校验。
  - 拒绝负数、非整数、溢出、倒序及超过 45 天的范围。
- 管理端列表支持 `before_id`，排序仍为 `id DESC`，返回 `next_cursor`。
  游标作用于已有筛选结果，不改变计数条件。
- 默认前端的两个管理端日志入口通过公共 API 接入游标。
  连续翻页、已访问的上一页使用游标；新的浅页码跳转兼容 OFFSET。
  旧客户端和直接页码跳转最多允许 10,000 条偏移，超过后必须使用游标。
  前端固定翻页时间窗口，按用户、筛选、页大小隔离游标，并限制内存容量。
- 精确计数按筛选和身份缓存 60 秒；键排除页码、页大小和游标，
  起止时间按分钟分桶。因此总数最多存在短暂延迟，列表内容不缓存。
  同键计数通过 singleflight 合并，不缓存失败结果。
- `/stat` 增加 singleflight、30 秒查询超时，并与 `/summary`、计数共用
  每应用进程 2 个聚合并发槽。列表另有每进程 2 个并发槽和 30 秒超时。
  多应用节点上限会相加，这不是整个集群只有 2 个查询。
- 用户和代理接口恢复原有查询语义，本次仅治理管理端接口。

## 索引复核

DB6 PostgreSQL 18，检查时间约 2026-09-09 07:53–07:58 UTC。
所有 SQL 使用只读事务、4 秒 statement timeout；没有执行 DDL、删除或统计重置。

此前用 `extract(epoch ...)` 直接比较的计划产生 `created_at::numeric`，
不能代表应用的 int64 参数。本次显式使用 bigint 时间戳：

| 样本 | 实际结果 |
| --- | --- |
| 最近 45 天消费日志 Count（仅 EXPLAIN） | `(type, created_at)` 的类型和起止时间全部进入 Index Cond |
| 最近一天首页 20 条 | 0.502 ms 执行时间、29 shared hits，使用现有 `(id, created_at)` |
| 最近一小时消费日志 Count | 11.607 ms、3,073 行、2,602 shared hits，使用 `(type, created_at)`；有 3,073 次 heap fetch |
| 45 天窗口跳过 10,000 条定位 ID | 101.112 ms、7,786 hits + 9 reads，访问 10,001 条匹配记录 |
| 同一位置 ID 游标取 20 条 | 0.934 ms、26 shared hits，匹配记录读取 20 条 |
| 用户时间窗口（仅 EXPLAIN） | 计数使用现有 token usage 组合索引；列表使用 `(user_id, id)` |

以上为少量在线样本，包含缓存冷热和查询列不同的影响，不能作为整体提速倍数或
P95/P99 指标。没有在生产执行完整 45 天 `EXPLAIN ANALYZE COUNT` 压测。

候选索引决策：

| 候选 | 当前决定 |
| --- | --- |
| `(created_at, id)` | 暂不新增；不能普遍替代 `ORDER BY id DESC` 的现有 `(id, created_at)`，时间范围索引不天然满足跨时间的 id 排序 |
| `(type, created_at, id)` | 暂不新增；现有 `(type, created_at)` 已支持过滤和计数，尾部 id 是否收益需要副本对照测试 |
| `(user_id, created_at, id)` | 保留候选；可能改善用户窗口计数，但新增前需评估现有两组用户索引和真实请求比例 |

没有新增 GORM index 标签，以免下一次启动自动迁移对生产建索引。没有移除任何
现有索引。累计 idx_scan/idx_tup_read 不等于最近半小时查询比例；目前没有
pg_stat_statements，不能用这些累计数据确定本次事故的根因。

若后续确需新增，在独立 PostgreSQL 副本中分别记录候选前后的
`EXPLAIN (ANALYZE, BUFFERS)`、索引大小、插入/更新耗时和 WAL 增量。
确认收益后再准备独立上线迁移；不同时叠加三组候选。
